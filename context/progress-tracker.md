## Architecture Decisions

- Used `shadcn@latest init -d` (tool defaults: template `next`, preset `base-nova`) rather than picking a specific preset/base library, since the spec didn't specify one and the CLI's presets (nova, vega, maia, lyra, mira, luma, sera, rhea) are unfamiliar/newer than training data — deferred to the tool's own recommended default.
- Component library is `@base-ui/react` (Base UI), not Radix UI — this shadcn CLI version's default, differs from the classic shadcn/Radix setup.
- Do not hand-edit `components/ui/*` — regenerate via `npx shadcn add <component> --overwrite` instead (per AGENTS.md/spec instruction).
- Sidebar open/close and navbar's icon state are lifted to the parent (`isOpen`/`isSidebarOpen` + callback props) rather than owned internally by either component, since the navbar's icon and the sidebar's visibility must stay in sync and future chapters will need to control both from a shared editor layout.
- `proxy.ts` uses the "protected-first" `clerkMiddleware` strategy (deny by default, allow-list `/sign-in` and `/sign-up`) rather than "public-first", per spec's "Protect everything else by default." Public paths are derived from `NEXT_PUBLIC_CLERK_SIGN_IN_URL`/`NEXT_PUBLIC_CLERK_SIGN_UP_URL` instead of hardcoded strings, so renaming those routes only requires an env change.
- `proxy.ts` now treats `/api(.*)` as a public route (bypassing middleware-level `auth.protect()`), added while implementing `06-project-apis.md`. This isn't a relaxation of protection — every `app/api/*` route still calls `auth()` itself and returns `401` JSON when unauthenticated, per `code-standards.md`'s "enforce auth ... before any mutation." It was necessary, not stylistic: verified empirically (`node_modules/@clerk/nextjs/dist/esm/server/protect.js`) that `auth.protect()`'s default `handleUnauthenticated()` redirects to `/sign-in` for requests it classifies as page navigations, and otherwise calls Next's `notFound()` (a **404**, not 401) for anything it doesn't recognize as a page or a server action — a plain `fetch()`-style API request gets a 404, which directly conflicts with the spec's explicit "unauthenticated requests return 401." Route-level `auth()` checks are the only way to guarantee the 401 contract this and future `app/api/*` specs require.
- `/` still does its own explicit `auth()` check + redirect in `app/page.tsx` (rather than relying solely on the proxy's automatic redirect-to-sign-in for unauthenticated visitors) since the spec calls out both directions of that redirect explicitly and the page-level check is correct regardless of how `proxy.ts`'s matcher/public-route list evolves later.
- `07-wire-editor-home.md`'s Create bullets ("generate a short unique suffix, slugify the name to create the room ID... the project ID and Liveblocks room ID should stay aligned") only make sense if the *database* project ID and the future Liveblocks room ID are the same value — otherwise "stay aligned" would require a separate mapping the spec never describes, and there's no `roomId` column in the schema to hold one. Rather than invent a mapping, extended `POST /api/projects` (from `06-project-apis.md`) to accept an optional client-supplied `id` — the client computes `slugify(name)-<shortSuffix>` (in `hooks/use-project-actions.ts`) and sends it as `id`; the server uses it as the Prisma primary key instead of the default `cuid()` when present, and returns `409` on a (extremely unlikely, 6-char base36 suffix) collision. This is additive/backward-compatible — omitting `id` behaves exactly as `06-project-apis.md` specified. No actual Liveblocks room is created yet (the package isn't installed) — this only guarantees that whenever Liveblocks does get wired up, `project.id` is already a valid, pre-aligned room name with no lookup needed.
- Shared-project listing (`lib/projects.ts`) matches on the requesting user's own Clerk-verified email (via `currentUser()`), not a client-supplied one — consistent with `architecture.md`'s "membership checks always use the authenticated Clerk user ID (never client-supplied email)" in spirit, even though the current schema can only join on email (see Open Questions).
- Deliberately skipped two CodeRabbit findings on the `07-wire-editor-home.md` PR: (1) `architecture.md`'s canvas-snapshot/spec-publication wording describes an atomic-claim protocol for Liveblocks/Vercel Blob/Trigger.dev — none of which exist in the repo yet; fixing prose for an unbuilt subsystem now means guessing at details (blob key naming, cleanup triggers) that should come from the actual canvas spec instead. (2) `06-project-apis.md` still reads "backend-only, do not wire the UI yet" even though `07` wired it up — left as-is because numbered `context/feature-specs/*.md` files are treated as historical asks in this project (see the "Did **not** edit their prose" note earlier in Completed), not living docs; `progress-tracker.md` already carries the "this was superseded by 07" cross-reference.
- `lib/liveblocks.ts#getLiveblocksClient` constructs the `Liveblocks` client **lazily**, inside the getter, instead of as a top-level `export const` (unlike `lib/prisma.ts`'s otherwise-identical caching pattern). Discovered empirically: Next.js's build-time "Collecting page data" step imports every route module to statically analyze it, which would eagerly run `new Liveblocks({...})` at import time — and that constructor validates the secret's `sk_...` format immediately, so any build without a real `LIVEBLOCKS_SECRET_KEY` set would fail outright (confirmed: it did, until this was changed). Lazy construction means the client is only ever built on an actual incoming request, so the build no longer depends on the env var being present or well-formed. `lib/prisma.ts` doesn't have this problem because `PrismaClient`'s constructor doesn't eagerly validate/connect.
- ~~`POST /api/liveblocks-auth` grants `defaultAccesses: ["room:write"]` when creating a room...~~ **Reverted — this reasoning was wrong and created a real cross-project access bug.** Found via a CodeRabbit review comment, confirmed by reading `@liveblocks/node`'s own types: `identifyUser` issues an access token scoped to the *user*, not to the `room` this route just checked — whether that token can actually connect to a given room is decided independently by that room's own `defaultAccesses`/`usersAccesses`. Since every room got created with `defaultAccesses: ["room:write"]`, any authenticated user who'd ever legitimately obtained a token for *one* project (by passing `checkProjectAccess` for it) could reuse that same token to connect directly to *any other* project's room — bypassing `checkProjectAccess` for those other rooms entirely, since the client never needs to call this route again once it has a valid token and knows a room ID (and project IDs are non-secret slugs). The original "this route is the sole gate" claim was false — the room's own permissions are an independent, parallel gate.
  - Fixed: `getOrCreateRoom` → `liveblocks.upsertRoom(projectId, { update: { defaultAccesses: [], usersAccesses: { [userId]: ["room:write"] } } })`. `upsertRoom`'s `update` fields apply on *every* call, whether the room is being created or already exists (confirmed via the SDK's own JSDoc) — so this both (a) grants explicit per-user write access only to whoever just passed this route's own authorization check, refreshed on every room-join rather than only at creation (solving the original "collaborator added later" concern the old design was trying to address, without needing a public default to do it), and (b) self-heals any room created under the old code the next time anyone in that project reconnects, since `defaultAccesses: []` is re-applied on every request, not just at creation.
